First-Session Freeze — Every Possibility

Fresh users, right after finishing onboarding: blank profile, then laggy / buggy / stuck pages (Trips Explore worst). Smooth during onboarding. Restart fixes it completely.

"Restart fixes it" + "starts at onboarding end" + "0 errors" together point at in-memory / in-flight runtime state created by the act of finishing onboarding — cleared only by process death. Two mechanisms fit best: bandwidth saturation from the just-started background video upload, and memory/main-thread pressure from work that piled up across the long onboarding. They are not mutually exclusive and probably stack.

1 · Bandwidth saturation leading theory

Finishing onboarding kicks off heavy background transfers with no throttling. They compete with the very network-hungry Explore screen for the uplink/downlink. Explains network-independence because it's self-inflicted congestion, and explains restart-fixes-it (killing the process kills the transfers).

▶ Profile video upload — raw, uncompressed, up to ~250 MB, fire-and-forget during landing HighCONFIRMED

On the onboarding video step, tapping Next starts the S3 upload without awaiting it and immediately advances — the user walks into the main app while the upload runs. The picked video is sent as-is, no compression. The processing poll is explicitly "sized for 250 MB videos," so the payload can be enormous. A large upload saturates the cellular uplink, and a saturated uplink cripples every download (images, feed) on Explore.

2 · Memory pressure → Hermes GC → progressive JS slowdown

"Restart fixes it" is the classic signature of a heap that grows across session #1 and is reclaimed only by process death. As memory climbs, Hermes GC pauses lengthen — the JS thread gets steadily slower ("laggy," "almost doesn't respond") without ever crashing. One prior Sentry event was an OS RAM kill (WatchdogTermination) on an iPad.

▶ Three session-replay recorders running at once, unmasked, screenshotting every second — across the whole long onboarding HighCONFIRMED (shipped)

The shipped build runs two PostHog clients (both with enableSessionReplay) plus Sentry's mobile replay (replaysOnErrorSampleRate:1 buffers continuously). All masking is off, so frames are full-fidelity and compress poorly. Each pipeline captures + encodes a full-screen bitmap ~every second, with main-thread phases. Onboarding is long (video record, forms, chat) — that's minutes of triple capture buffering before the user even reaches Explore.

3 · JS-thread wedge / starvation (permanent until restart)

The "taps do nothing, 0 errors" signature can also come from a JS thread that stops being serviced. Native scroll keeps working (janky), JS-dependent taps die. These mechanisms must START at onboarding-completion and PERSIST — a one-shot hang that resolves wouldn't match.

▶ Un-timed Supabase requests hang forever (RN fetch has no default timeout) PlausibleCONFIRMED

React Native's fetch defaults timeout=0 (no OS timeout), and supabase-js adds none — a request on a stalled connection can wait indefinitely, stranding anything awaiting it. auth-js 2.110.7 routes every call through a shared init promise and a single-flight refresh promise, so one stuck request can stall unrelated calls app-wide (the old "lock" claim was for ≤2.80.0 / builds ≤44 — disabled by default in 45/46).

4 · Blank profile — the specific first symptom

This one we traced end-to-end and it is the best-understood part.

▶ Fresh user has no cached profile → a hung fetch leaves the loading gate up forever HighCONFIRMED

loadProfileData sets authChecking=true and the render gate if ((loading || authChecking) && !profileData) shows header-only + blank body. A returning user has cached profileData so the gate falls through; a brand-new user has nothing cached, so if the profile fetch (or the auth call) hangs on a stalled/ saturated connection, the gate stays up permanently — the blank profile with just the name in the header, exactly as screenshotted.

5 · Why Trips Explore specifically

Both reports name the Explore deck. It's the heaviest screen at the worst moment.

▶ Hard virtualization + native-driven deck = "slow and stuck" the instant JS is starved PlausibleCONFIRMED behavior

The deck mounts only ~2–3 cards (initialNumToRender=2, maxToRenderPerBatch=3, windowSize=3, removeClippedSubviews) and drives the card transforms natively (useNativeDriver:true). When JS is starved (by §1/§2), native scroll keeps moving but new cards can't mount and snapToInterval snaps back over empty slots — producing exactly "swipes work but slow and stuck," while taps (which need JS) do nothing. So Explore doesn't cause the freeze; it's the screen that most vividly shows a starved thread, and its cold-cache image loads also feed the congestion/memory.

6 · Why we've been blind (meta)

Every one of these failure modes is invisible to our current telemetry — which is itself a finding, and part of why this dragged on.

▶ The js_thread_stall alarm never sent a single event (dead wire) CONFIRMED

The watchdog reported via posthogService.trackEvent, whose initializePostHog() is never called anywhere → silent no-op in every build. So "no js_thread_stall in PostHog" meant "the wire was cut," not "no freezes." Also: it's a JS setInterval, so during a total wedge it can't fire at all, and an app killed while frozen never reports.

The failure throws nothing (a hang / GC-stall isn't an exception), so Sentry/PostHog "Errors: 0" is expected, not reassuring. Examined and largely cleared

Auth-lock deadlock in shipped builds
The internal auth-js "lock" is null by default in 2.110.7 (builds 45/46) — verified in installed source. Real only for ≤2.80.0. The init/refresh promises (§3) are the surviving app-wide choke points.
Unbounded retry loops / compounding timers on the fresh-user path
All production setIntervals are bounded: video poll (28×), presence heartbeat (fixed 60s, backoff capped at 10), preload check-loops clear on ready/timeout. No backoff-free retry found. (ProfileScreen video poll caps at 210 attempts and only runs on manual upload.)
Skeleton / spinner animations pegging JS
Shimmer, profile upload spinner, pulse all use useNativeDriver:true → native thread. They do not peg JS while data hangs.
InteractionManager leak
Nothing on the tap→push path holds an interaction handle; no JS-driven animation on the fresh-user Trips tree that could leak one.
Server-side / persisted-state cause
Ruled out by "restart with the same account fixes it" — session #2 uses identical token/data and works.
