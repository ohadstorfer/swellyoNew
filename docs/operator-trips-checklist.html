closed

A cancelled trip still takes money — and refunded nobody19 aug

The note here used to say "one status = 'active' check". That check is in, and it was the smaller half. payments-checkout (v19, deployed) now refuses a trip that is not active with a 409 and a line written for the traveler holding the payment screen — they did nothing wrong and are about to lose a trip, so it says what happened rather than just refusing. Cancelled and completed get different sentences; the check sits after payment_mode so an offline trip keeps its own message, and before capacity so a cancelled trip is never called "full".

The bigger half is that cancelling now pays everyone back, which nothing did before — it was one of the three go-live blockers. A new trip-cancel function refunds every traveler in full, and the policy does not apply: those terms govern a traveler who backs out, never an operator who calls the trip off. Airbnb, Eventbrite and GetYourGuide all draw the line in the same place. So the function takes no amounts from the client and has no partial mode — the refund is not the caller's decision.

Order is the load-bearing part: cancel first, then expire the open Checkout Sessions, then refund. Refunding first would leave a window where someone pays into a trip already being wound up and misses the batch. The session sweep is best-effort — Stripe pages that list at 100 platform-wide — which is exactly why the server-side status check has to exist too, and stay. Re-running is safe: an already-cancelled trip falls through to the refund sweep, so the client's Retry only re-attempts what did not finish, and a double tap cannot double-refund.

It also refuses rather than guesses. A refund it cannot price in the operator's own settlement currency is blocked, not attempted, and an operator with too little balance gets blocked_insufficient_balance per traveler instead of a half-done batch. Refund rows go to organized_trip_refunds only — the ledger's refunded events stay the webhook's job, because a second writer would double-count its cumulative maths.

Live. Function deployed, checkout redeployed, and the audit migration (cancelled_at / _by / _reason) applied to prod — who pulled the trip, when and why, which was never recorded before and is not backfillable. One thing to know: the refund core in trip-cancel is a hand-kept copy of payments-refund's, since this repo has no shared-module convention for edge functions. Change one, change both — that drift has already cost 12% of the balance headroom once, when one copy read amount where it had to read net.

closed

Deadline reminders never fire on their own20 aug

The due-soon and overdue notifications existed and rendered — but their only producer was the operator pressing "Remind" on the dashboard. The daily job covered trip start and end, not requirements. A traveler could sail past every document deadline in silence, and the operator was not told either — operator_requirement_overdue_operator had existed in the enum since July with no producer at all.

Scoped to document deadlines (DOC-2/DOC-3/OPS-2 in the notifications plan) — not payment deadlines (PAY-1..4), which the plan leaves as an open product decision ("decide the real consequence" for a late deposit). A new RPC, operator_requirement_deadline_owed, is a hand-kept copy of operator_remind_requirement's own "who still owes this" logic — same reason trip-cancel keeps its own copy of the refund core: a definer function is the security boundary, so duplicating it here is safer than threading a shared helper through the RPC that already has a client contract.

A new daily cron, scan-requirement-deadlines, reads it per trip and writes two things: the traveler side at -14/-7/-3/-2/-1 days before due and +1/+3 after (matching the existing copy's cadence exactly), and one operator digest per requirement — never one push per stuck traveler — once the deadline is a day out or past, repeating at most every 20 hours while anyone is still owed. Deliberately excludes anything already rejected: that has its own live notification naming exactly what to fix, and re-nagging it on a timer would just be a second, vaguer message about the same thing.

Idempotency needed no claim column: the traveler side dedupes on (recipient, requirement, exact day offset) read straight from notification history, the same pattern scan-trip-reminders already uses for its own stages. The operator digest has no natural per-requirement column to claim, so it reads its own last-sent time from the same table instead.

operator_requirement_overdue and operator_requirement_overdue_operator had no copy anywhere — not a template row, not a fallback, not a client type — so producing them today would have rendered as the generic "Notification" fallback the checklist's own footer warns about. Both now have real copy in dispatch-notification-queue/render.ts and in the client, with no template row on purpose: the text needs a formatted due date and a headcount, and neither {date} nor {count} is a var either renderer's fill() resolves — the same reason operator_stripe_action_needed has no template row either.

Live 20 Aug. Applied and deployed in order: operator_requirement_deadline_owed on prod, scan-requirement-deadlines deployed, smoke-tested by hand (200, travelerNudges: 0, operatorDigests: 0 — nothing due today, nothing sent), then dispatch-notification-queue redeployed with the real copy for both overdue types, then the cron (jobid 12, 35 7 * * *). Caught one thing on the way: this same deploy pass had to fix a live-blocking typo in render.ts's brand-new member_removed refund copy (d.refund_usd where the param is named data) — the function would not have compiled otherwise, blocking this deploy and the remove-refund work in the row below it, which landed in the same window.

built

A chargeback is invisible20 aug

Was: a traveler disputes a card charge → no row is written, nobody is told, and every money total is silently wrong from that day on. Disputes can arrive up to ~18 months after the charge.

Built 20 aug — Phase 3 of the refunds spec, on "do it". The webhook now handles charge.dispute.created (a 0-amount disputed marker in the ledger, plus a quiet-hours-bypassing push to the operator naming the amount and the evidence deadline — the one dispute moment with a clock on it) and charge.dispute.closed. A dispute lost first pulls the operator's share back with a transfer reversal — reverse-on-loss only, per Stripe's cross-border warning; idempotent by dispute-id metadata; recovery ordered before the ledger write so a failed reversal retries — then writes a negative dispute_lost row. Every money total in the app, the web dashboard and operator_requirement_pay_state sums non-failed rows, so they all self-correct on that row with zero changes: the traveler who charged back simply owes again. A dispute won writes nothing (no money moved) and just tells the operator. All three migrations are APPLIED to prod; the three ledgers label the new rows (Chargeback chip / "Dispute opened") instead of calling them "Payment". Step 4 of the plan turned out to need no code: debit_negative_balances already defaults to true for our Express configuration, so Stripe auto-debits the operator's bank when the reversal sends them negative (AU/CA/SEPA+UK/NZ/US banks only).

⚠️ Not live until four clicks that were blocked on a wrong login. The Supabase CLI and the browser are both signed into an account that cannot see the Swellyo project, so two deploys are pending: stripe-webhook (the handler) and dispatch-notification-queue (the push copy — deliberately no template rows, the copy needs amounts and dates). And the sandbox webhook destination must subscribe charge.dispute.created + charge.dispute.closed — dashboard-created, so no API can add them. Until then Stripe never sends the events and the code sits idle rather than failing. The live-mode flip now needs SIX events; PRE_BUILD_CHECKLIST is updated.

closed

Stripe breaking is silent18 aug

Built. Four things now speak: Stripe closed the account, payments stopped, payouts frozen, and a deadline already missed while the account still works — that last one being the only one that arrives while there is still time to act. The first two bypass quiet hours; an operator whose payments have stopped is better woken than left selling.

It is a trigger on the payout row, not a branch in the webhook, and that is the whole point. Three different things write that row — Stripe's webhook, the onboarding poll, and a new daily sweep — and any of them can be the one that notices. Putting the rule in the row means all three fire it identically, the same way cancel and remove are triggers so the web dashboard notifies exactly like the phone. "Stripe approved you" moved there too: it used to depend on a webhook endpoint registered in a dashboard nobody re-checks, which is the same single point of failure that left the payment ledger empty for six days in August.

The daily sweep re-reads every connected account from Stripe whether or not the webhook is alive, so this can no longer break by something being quietly unregistered. It is scheduled and running as of 19 August, 05:40 UTC. Live and proved: the sweep was run once by hand against the real account and returned refreshed: 1 while sending nothing, and the trigger was walked through all four failures inside a transaction that was then thrown away — the escalation from "deadline missed" to "payments stopped" to "account closed" produced three separate alerts, and a rejected account produced one, not three.

A failed payment told nobody19 aug

A card declined, or a checkout opened and abandoned, and the traveler heard nothing — they found out when the operator chased them. The old note in the plan said the server could not know, because the attempt only existed on the phone. That was wrong: Stripe says both, payment_intent.payment_failed and checkout.session.expired. We simply were not subscribed.

Now handled, and the interesting part is everything it refuses to send. Checkout deliberately expires its own stale-priced sessions when a price is edited, so an expiry with a live replacement is someone mid-payment, not someone stuck. It also stays quiet when the money arrived another way, when the trip is cancelled or already departed, and more than once per requirement per day. Best-effort by design — it never fails the webhook, so it could not start a retry storm even before the migrations landed.

A payment can reach Stripe and never reach us19 aug

The one that already happened, and the reason the row above exists at all. The platform webhook destination went missing twice in August; payments succeeded, the ledger stayed empty, and nobody noticed for six days — four payments, $3,500, and a traveler who had overpaid by $600 while the app kept asking for more.

closed

Deposit paid, onboarding abandoned — and nobody notices18 aug

Built. The traveler is nudged four hours after they stop, again at 24 hours, and then every 24 hours for as long as they stay stuck. Four hours is short on purpose: most people who abandon a form abandon it in the same sitting, and a nudge that lands while they still remember what they were doing is worth more than three polite ones spread over a week. Each one names the steps actually blocking them, because someone who stopped because they were unsure which step it was is not helped by "you have steps left".

The operator joins at the 24-hour mark and hears daily after that — one digest per trip, never one push per stuck traveler — and the trip page carries it as a to-do from the same mark, so the banner and the notification can never disagree. The first four hours stay the traveler's alone; handing the operator a chore that usually resolves itself is how a to-do list stops being read.

The repeat has no end, and does not need one. The clock runs from the traveler's last action, not the deposit, so the only thing that silences it is the problem going away — they act, or the trip starts, or it is cancelled. Someone steadily working a long list is never nagged.

Re-timed 19 August from the original 24h / 3 days / 7 days ladder, which ended in silence. The three sent-at columns could not express a repeat and were replaced by a stage and an anchor — the anchor being what lets one late upload restart the ladder instead of buying permanent quiet. The cron moved from daily to hourly in the same change: on a daily schedule "four hours" would have quietly meant "tomorrow morning".

Live since 18 August — functions deployed, cron running, migration applied.

A new waiver quietly un-signs everyone18 aug

Closed by removing the ability, not by adding a notification. The waiver freezes the moment anyone is affected — but stays swappable while the trip is empty, so an operator who uploaded the wrong PDF is not stuck with it.

"Empty" is two tests, and the second is the one that matters: no travelers, and no signatures from anyone. A member count alone would have been wrong twice over — every trip carries its own host as a member, so the door would never open; and crew sign the same document without being members, so a trip with zero travelers can still have a signed photographer. A trigger checks both inside the write, so someone joining while the operator picks a file loses the race safely.

Moving the dates moves every deadline in silence19 aug

Due dates are counted back from the start date, so changing it reschedules every document and the final payment. That part stays — it is why moving a trip needs no backfill. What changed is that it is no longer silent, on either side.

The operator is told before they confirm, and the final payment gets its own sentence with its new date on it, because that is the one nobody has in mind while dragging a calendar. Documents are a count next to it, and anything landing in the past is still called out. The old line asking the operator to go tell people themselves is gone — the popup now says we do.

We do, from a trigger on the row rather than from the edit screen, so changing the dates from the dashboard or by hand in SQL notifies exactly the same. Everyone on the trip hears, including travelers part-way through onboarding — the dates are half the deal they are in the middle of accepting. Hosts are excluded by role, not by the trip's host_id: that column only names the primary host, so the older test would have told a co-host about their own change.

Applied 19 aug, both migrations, and proven on prod in a rolled-back test: moving El Salvador 26 by three days wrote one notification to each of its 3 travelers, queued 3 pushes, and read back 13 Jan – 23 Jan 2027 with has_deadlines true — then rolled the whole thing back, so nothing was sent and the trip's dates never moved. Push copy ships as a template row, so the dispatcher needed no deploy; the trade is that the push says "the dates changed" while the bell names them, until that function is next deployed.

holds

Refund math is self-correcting

Refunds land as negative payment rows, so every "paid" number in the app, the dashboard and the server subtracts them by plain sum. Partial and repeated refunds compute the delta from Stripe's cumulative figure, so a redelivered webhook cannot double-count.

holds

Over-approving is safe end to end

Approving takes no seat. The seat is claimed at the end of onboarding under a row lock, and checkout refuses the deposit when the trip is already full — before charging. The operator can approve 14 people for 10 spots and the boat fills in finish order.

holds

Repricing never touches an existing deal

Changing the trip's price pins everyone already on it to their current price first, then reprices, then syncs the pay rows — and if the pinning fails, the new price is not written. A per-traveler price set by hand is never second-guessed by anything.

holds

Cancel, leave, remove and decline all notify — from any client

They are database triggers, not app code, so cancelling from the web dashboard fires the same notifications as cancelling from the phone.

holds

Refunds still work on a cancelled trip

The one payment path that must stay open after cancelling, and it does — checked deliberately, since the checkout hole above is the same missing status read in the other direction.

holds

Signatures are evidence, not checkmarks

Waiver and policy consents store the exact text version, a hash, the typed name, IP and timestamp — enough to answer "what exactly did they agree to, and when" years later.

Deliberately not done

None of these was on your list. They are either known gaps from the staff spec or a second pass — worth a decision, not a surprise.

  • Staff get no notifications

    The fan-out builds its admin list from participants with the host role and does not know the staff table exists. An invited guide is never told, and a manager misses every document and payment notification. Its own piece of work.

  • Staff are not in the group chat

    The chat capability is granted by the Guide and Manager tiers and wired to nothing — a guide needs a conversation membership, which is a separate permission system. So the chat button stays host and member only, on purpose: a button that errors is worse than no button.

  • Inviting travelers is still host-only

    A manager reviews join requests and removes people, but does not invite. Not asked for — say the word and it is one gate.

  • The web operator dashboard is untouched

    Its Crew page already did the document review the app just gained. Nothing there regressed, and nothing there gained the new capabilities either.
