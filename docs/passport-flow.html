Passports on Group Trips

How uploading, reading, storing and serving a passport works — and the one decision still open.

Why we collect it at all: the operator books flights for the group. An airline needs the seven fields printed in the passport. It does not need the picture.

The big idea

We are not "using AI to read a document." A passport is already machine-readable by design. At the bottom of the page there are two lines of chunky monospace text:

PPGBRSPECIMEN<<ANGELA<ZOE<<<<<<<<<<<<<<<<<<<
5334755193GBR8812198F3009286<<<<<<<<<<<<<<00
This is the MRZ — Machine Readable Zone. It exists so border e-gates can read passports. It holds all seven fields we need.

The MRZ has check digits built in — small checksums that prove the read was correct. Tested locally with the free mrz package:

  • Valid MRZ → VALID: true, all seven fields extracted.
  • One digit of the passport number changed → VALID: false, failed checks: Document number check digit, Composite check digit.
This is the whole answer. We cannot silently get wrong data. Either the checksums pass, or we ask the traveler to scan again. It also removes the usual worry about AI reading documents — a made-up number fails the checksum.
2026 standard change. Since 1 January 2026, ICAO requires a two-letter document code (PP for an ordinary passport) instead of one letter. Both P and PP parsed correctly in the test. Do not write our own regex for this — use the maintained package.

The whole flow

  1. Traveler

    Asked

    The trip has a "passport" requirement. It shows up in the traveler's checklist.

  2. Traveler

    Photographs the passport

    The page with the two machine-readable lines.

  3. Not decided yet

    The lines are turned into text

    This is the only real decision left. Three routes below.

  4. Automatic

    The maths is checked

    The mrz package parses the text and validates the check digits. Pass → continue. Fail → "that didn't scan clearly, try again."

  5. Traveler

    Confirms the seven fields

    Never skip this. Checksums prove the read is right — not that it is the right passport, or that the operator will accept it.

  6. Server

    Stored, in three different ways

    The photo → private bucket, never public.
    The six ordinary fields → plain columns.
    The passport number → scrambled with a key that lives outside the database.

  7. Operator

    Served

    The operator opens the trip, reads the seven fields as text, and books the flight. If they want to look at the photo they get a link that dies after 60 seconds. Only the traveler and the trip host can get that link.

  8. Automatic, nightly

    Deleted

    30 days after the trip ends, the photo is deleted and the passport number erased. The six ordinary fields stay, so a repeat traveler does not retype them.

Step 3 — how to read the lines

A. On the phoneBest privacy

The camera reads the lines on the device. The photo never leaves the phone to be read. Either a free option (VisionCamera + Google MLKit text recognition) or a paid SDK (Dynamsoft MRZ Scanner — near-100% accuracy, fully offline).

  • + No third party ever sees a passport. Works with no signal.
  • + Nothing to add to the privacy policy.
  • − It is a native module — it will not work in Expo Go. Needs a dev build to test at all.
  • − The most work of the three.
B. On our serverWould skip

The photo is already going to our private bucket. An edge function reads it there.

  • B1 — OpenAI vision. No new vendor account, we already use them. But the passport photo goes to OpenAI, who keep API data up to 30 days unless we hold a zero-retention agreement. They become a subprocessor we must disclose.
  • B2 — A dedicated passport OCR API. Mindee, Klippa, Regula, Base64.ai. Built for exactly this, priced per page, free tiers exist, proper data-processing agreements. Cleanest server option, but a new vendor.
  • B3 — AWS Textract. Plain text detection is enough, because the MRZ is just printed text. AWS already holds our images, so no new company enters the picture.

+ Easy to build, works in Expo Go.  − The passport travels to someone else's computer to be read.

C. Typed by handShip this first

No scanning. Seven fields, a form.

  • + Zero new vendors, zero new disclosure, works everywhere.
  • + Already built — the save action.
  • − Typos. And a typo on a flight booking costs real money in airline name-change fees.
Recommendation: ship C now, add A later. Not as a compromise — C is not optional anyway. Worn passports don't scan, bad light doesn't scan, some travelers won't give camera access. Every scanning route needs a typed fallback underneath it, so build the floor first. Then add on-device scanning on the next native build as a pure speed upgrade, and we get the strongest privacy answer if anyone ever asks.

Route B is worth skipping entirely. Sending passports to a third party to read them is the one part of this flow we can avoid completely — and route A avoids it while being better on privacy, not worse. B only wins on "we want scanning this week without a native build." If that is the real constraint, B3 (AWS) is the pick, because AWS already holds our images.

One thing worth revisiting once A is in place: if the phone extracts the fields, do we still need to keep the photo at all? The operator books from text. If they don't need to eyeball the document, the photo could be optional per trip — and a photo we never stored cannot leak.

Decisions already locked

DecisionChoiceWhy
Passport number Stored, encrypted AES-256-GCM. Key lives in Edge Function secrets, never in the database — so a database dump holds ciphertext and nothing that opens it. Wiped by the 30-day purge, unlike the other fields.
Access logging No log Access rules are the only gate. If a passport ever leaks there is no list of who opened it. Easy to add later.
Photo retention 30 days after the trip ends Also applies to someone who leaves or is removed. The six ordinary fields survive on purpose.
Signed link life 60 seconds A signed URL is a bearer token — whoever holds the link has the file until it expires, logged in or not. Everything else in this app signs for an hour; documents do not.
Who can see it The traveler, or a trip host Nobody else. No public URL, ever. Documents never enter the thumbnail or video pipeline, so there are no untracked copies.

The open question

Is "scanning must work in Expo Go" a hard requirement — or are we fine typing the fields until the next native build?
