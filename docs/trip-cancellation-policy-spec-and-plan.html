Cancellation policy on the trip — spec & plan

11 August 2026 · rev 1 · operator trips (type C)

What we are building, in one breath.
  • The operator's policy is copied onto the trip when it is published, and frozen there.
  • The traveler reads it before they pay — in the app, and on the Stripe page itself.
  • Changing your default later never touches a trip you already sold.

Why this is needed

Today the policy exists only as an operator's private default. No trip carries one and no traveler screen reads one. So an operator can pick "No refunds", and the person paying a $500 deposit is never told.

Part 1 — The spec

The rule

Frozen at publish, never read live

The trip keeps its own copy of the policy. Nothing ever reads operator_settings to show a traveler anything.

Same reasoning as the default waiver: an operator who switches their default to "No refunds" in March must not silently rewrite what someone agreed to in January.

Right: trip stores standard → traveler sees "Full refund up to 60 days before".
Wrong: trip reads the operator's current default → the terms change under the traveler's feet.
No policy is a real state NULL ≠ "no refunds"

Type A and B trips have no policy at all, and so do the 23 operator trips that already exist. cancellation_preset = NULL means not specified.

The traveler UI shows nothing in that case — no section, no line at checkout. We do not backfill old trips from the operator's current default: that would be inventing terms for trips already sold.

Where the traveler sees it

MomentSurfaceWhat shows
Browsing — Nothing. No new section on the Plan tab (Ohad, 11 Aug). The policy is shown at the moment money moves, not while browsing.
Paying the deposit Stripe Checkout page The policy above the Pay button. The only place it can go — see below.
Paying the balance PayAmountSheet + Stripe page One line in the sheet, full text on the Stripe page.
The deposit has no in-app payment sheet.
  • From TravelerOnboardingScreen: "the deposit has no sheet, it goes straight to Checkout".
  • A deposit is all-or-nothing, so PayAmountSheet is never opened for it.
  • That means the Stripe page is the only surface between the traveler and the first, largest payment. Putting the policy there is not a nice-to-have.

What the Stripe page shows

Stripe Checkout takes custom_text[submit][message] — free text rendered directly above the Pay button. Max 1200 characters.

Example rendered on the Stripe page:
Cancellation policy — Cancel 60+ days before: 100% back · Less than 60 days before: nothing. Refunds are paid by the trip operator, not Swellyo.
  • Built from the same explain() the app uses, joined with " · ".
  • Truncated to 1200 chars, because a long "Notes" field can blow the limit and Stripe would reject the whole session — no payment at all.
  • Ends with who pays refunds. On an operator trip the money is in the operator's Stripe account and Swellyo has no refund path, so the page must not imply we do.
  • Omitted entirely when the trip has no policy. No empty label.

Considered and rejected: a required tick-box

Stripe also offers consent_collection[terms_of_service] = required, which forces a checkbox and records consent on the session. Rejected for now:

  • It needs a hosted URL for the terms. We have no public page per trip.
  • The traveler already signs a waiver in onboarding — a second forced agreement at the till is friction on the step where people abandon.
  • Worth revisiting when there is a real terms page.

Where the operator sets it

  • One card on the budget step of the wizard (already titled "Pricing" for operator trips).
  • Pre-filled from their onboarding default. Leaving it alone is the skip.
  • "Change" opens the existing CancellationPolicySheet — the same control as Settings, so the two cannot drift.
  • Not a new wizard step. It is a term of sale, like the price, and it belongs next to the price.
Part 2 — The plan

Step 1 — Migration needs applying by hand

alter table public.group_trips
  add column if not exists cancellation_preset text,
  add column if not exists cancellation_rules  jsonb not null default '[]'::jsonb,
  add column if not exists cancellation_notes  text;
  • Same column names as operator_settings, so toPreset, rulesFromWire, explain and summarise all work on a trip with no new code.
  • Additive and nullable — safe on the 23 live trips.
  • Plus a CHECK on the preset values, matching the one on operator_settings.
The trap: do NOT reuse normalise_operator_cancellation on this table.
  • It opens with if new.cancellation_preset <> 'custom'.
  • When the preset is NULL, that comparison is NULL — not true — so it falls through to the custom branch and raises "A custom cancellation policy needs at least one rule".
  • That would break creating every type A and B trip.
  • Fix: a separate trigger function for trips that returns early on NULL, then runs the same checks. Do not edit the shared one — operator_settings depends on it.

Step 2 — Types tiny

  • Three fields on GroupTrip and CreateGroupTripInput.
  • createGroupTrip does .insert({ ...input }) — a spread — so no service change.
  • getTripById does select('*') — so the detail screen gets the columns with no query change.
  • The feed RPCs (explore_feed, my_trips_feed) are untouched. The policy is not card data.

Step 3 — Wizard

  • Add the policy to WizardState, seeded from the operator's default.
  • Read it defensively so WIZARD_STATE_VERSION does not need bumping — an old saved draft simply lacks the field and falls back to the default.
  • One card on the budget step; "Change" opens CancellationPolicySheet.
  • At publish, the three values go into the create input.

Step 4 — Traveler, in the app

  • One summary line in PayAmountSheet (balance payments only — the deposit never opens it). Hidden when the trip has no policy.
  • No Plan-tab section. Cut deliberately: it is one more block of small print on a screen that already has plenty, and the place a refund rule actually needs reading is the screen where money is about to move — which is the Stripe page, covered in Step 5.

Step 5 — Traveler, on the Stripe page

Two edits in supabase/functions/payments-checkout/index.ts.

  1. Add the three columns to the trip select. It currently reads 'id, title, host_id, payment_mode, max_participants' — an explicit list, so the new columns will not arrive on their own.
  2. Add custom_text[submit][message], built from explain() and capped at 1200 chars.
Bump the idempotency key.
  • The file says: "BUMP THIS STRING whenever any field of the create call below changes."
  • checkout:m2: → checkout:m3:.
  • A key reused with different parameters is a 400 from Stripe, not a replay. The comment records that this exact mistake took the whole payment flow down once.

Deploy order

  1. Migration by hand.
  2. Deploy payments-checkout — safe before the client ships: with no policy on any trip yet, the new text is simply omitted.
  3. Ship the client.

Out of scope, on purpose

  • Editing the policy on a published trip. Changing terms after people have paid is its own decision — who gets told, and whether old participants keep the old terms. OperatorTripEditScreen stays as it is.
  • Actually processing refunds. Swellyo has no refund path. The policy is a promise the operator makes and pays from their own Stripe account. Every string we write must keep saying that.
  • Backfilling the 23 existing trips. They stay NULL.

How we will know it worked

  • Publish an operator trip with "No refunds" → the Plan tab shows it.
  • Start a deposit payment → the Stripe page shows it above the Pay button.
  • Change the operator default afterwards → the published trip is unchanged.
  • Create a type A trip → still works (the NULL-preset trigger trap).
