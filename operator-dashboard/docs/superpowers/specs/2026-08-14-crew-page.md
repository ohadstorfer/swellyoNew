# Crew on the dashboard

Managing the people who run a trip, from the desktop site.

**Status:** BUILT, 14 August 2026. Decided in an interview with Ohad, then built the
same day. Uncommitted.

The one migration it needed — `20260814000000_requirement_kind_unique_per_audience.sql`,
which fixes a bug older than this page — was **applied to production on
14 August 2026**. See §5.

**Why:** the app can already do all of this (`TripStaffSheet.tsx`). The operator
sitting at a desk reviewing sixty passports should not have to pick up their
phone to change one guide's tier or ask the photographer for a visa.

---

## 1. Rule 1 holds — nothing new in the database

Every read and every write below already exists and is already permitted.
This project adds no table, no function, no migration.

| What the page does | What it uses | Who it lets through |
|---|---|---|
| Show the crew | `select` on `organized_trip_staff` + `surfers` | `ots_select` — the owner, anyone on the trip, or yourself |
| Change a tier, title, bio, name | `update organized_trip_staff` | `ots_write` — **`group_trips.host_id` only** |
| Remove someone | `update … set revoked_at` | same |
| Find someone to invite | `search_users_for_staff(trip, query)` | `authenticated` |
| Invite them | `invite_staff_member(...)` | operator, checked inside the RPC |
| Tick what you need from them | `organized_trip_staff_requirements` | `otsr_write` = `trip_staff_can(trip,'staff.manage')` |
| Create a requirement row on first tick | `insert organized_trip_requirements` | `organized_trip_req_write` = `trip.edit` |

The one thing to know: **`staff.manage` is held by the operator of record and
nobody else.** `my_trip_capabilities()` returns the whole operator set when
`host_id = auth.uid()`, and no assignable tier carries `staff.manage`. So
gating this page on `can('staff.manage')` is exactly "is this the operator",
without the page ever asking what tier anyone is.

## 2. Who sees it

Operator only. A Manager gets into the dashboard on `docs.view` and reviews
documents; they never see a Crew link. This is invariant I2 from the staff spec
— only the operator writes staff — and the page follows it rather than showing
controls the database would refuse.

Hide the link, and guard the route. A Manager who types the URL gets sent back
to the trip, not shown an empty page.

## 3. Where it lives

Its own route, `/trips/:tripId/crew`, reached from a link on the trip page.
Like Money. The trip page already carries Documents, Other requirements,
Medical flags, Surf stats, Travelers and Money; crew management is three
different jobs and does not belong on the end of that scroll.

## 4. What the page does

### The list

Everyone on the crew, lowest tier first, same order the app uses. Each row:
photo, name, what they do, and a tier pill. Two states worth showing plainly:

- **Invite not accepted yet** — they have an account and a row, but have not
  accepted. Same wording as the app.
- **Listed** — no account. A credit on the trip page, no access to anything.

### Editing one person

Clicking a row opens their detail. What is editable depends on whether there is
an account behind the row — the test is `user_id`, never `role_key === 'listed'`,
because someone can accept an invite at the Listed tier and still be promotable.

| Field | Has an account | Listed (no account) |
|---|---|---|
| Tier | editable — the five cards, capabilities drawn from the DB | not offered; there is nobody to grant access to |
| Title ("Head guide") | editable | editable |
| Bio | editable | editable |
| Name | **read-only, from their Swellyo profile** | editable |
| Photo | read-only, from their profile | **app only** — the dashboard has no upload path |

Name and photo for an account holder are deliberately not overridable. One
source of truth: a person renames themselves once and every trip they crew
follows. The operator owns how the person is *introduced* — title and bio —
because the same guide is "Head guide" on one trip and "Photographer" on the
next.

The tier cards render `role.capabilities` **from the database**, exactly as the
app does. Never a hardcoded list — that is the whole point of the permission
design. The dashboard already owns the English for each key in
`services/access.ts`; reuse it, do not write a second copy.

### Paperwork

The same tick list the app has (`StaffPaperworkSection`): Passport, Visa,
Waiver, Medical info, Insurance, Flight details. Ticking assigns; unticking
unassigns and never deletes the document the person already sent.

The list is the **catalog**, not the trip's existing requirements. A trip that
has never asked crew for anything still shows six rows, and the first tick
creates the requirement row. This is why: the earlier version showed an empty
box telling the operator to go and make a requirement somewhere else, and
nobody ever did.

Show who has sent what, as status only. **No opening the file, no approve or
reject** in this version — that is document review, and it lives where document
review already lives.

No deadline and no overdue state, matching the app. Staff paperwork is flagged,
never gated: a countdown that locks the guide out two days before departure is
a worse outcome than the missing certificate.

### Adding someone

**Search by name, invite in app.** Type two or more characters, pick the
person, choose their tier, tick what you need from them, send. They get a
notification; accepting runs the same `accept_staff_invite` path a link uses.

`search_users_for_staff` already excludes the operator, current crew, travelers
on this trip, anyone with an invite waiting, and blocks in both directions. It
returns a `state` for the first three so a blocked row can be shown dimmed with
the reason, rather than the person quietly not appearing.

**Not on desktop:** invite links and Listed credits. Both stay in the app — the
link because sharing it is a phone action anyway, the Listed credit because it
needs a photo upload the dashboard cannot do yet. An existing Listed row is
still editable here (name, title, bio).

### Removing someone

Allowed, with a confirm dialog first. It is a soft revoke — `revoked_at` is
stamped and the row stays, so "who could see the passports in July" stays
answerable — but their access stops the moment it lands, so it gets a
confirmation, not a bare button.

## 5. What was found while building it

Three things, all older than this page.

**A crew requirement cannot be created on any trip that exists.**
`uq_organized_trip_req_kind_per_trip` is unique on `(trip_id, kind)` and was
never widened when `audience` was added, so one trip cannot hold both a
traveler passport and a crew passport. All 4 operator trips on production ask
travelers for at least one of the six crew kinds, so the tick fails on every one
of them — in the app's crew sheet too, which shipped a day earlier. Nobody has
hit it because there are 0 staff-audience requirements yet.
`20260814000000_requirement_kind_unique_per_audience.sql` widens it to
`(trip_id, kind, audience)`. **Applied 14 August 2026**, after checking that the
wider key has no duplicates, that no constraint owns the index, that no function
names it, and that the table is 28 rows. Verified afterwards by inserting a crew
passport onto a trip that already has a traveler one, inside a DO block that
raised to roll itself back.

`friendlyStaffRequirementError` stays: it is a one-line guard, and the next
person to add a kind to a trip that already has it will meet the same 23505 from
a different direction.

**Every traveler photo on this site was missing.** `fetchProfiles` read
`surfers.profile_photo_url`; the app writes `profile_image_url` and never
mentions the other. 232 of 685 surfers have a photo, 1 has the column this site
read. Fixed.

**Crew requirements would have polluted the traveler review.** `fetchTripReview`
takes every active requirement on the trip, and
`organized_trip_requirements_resolved` does not carry `audience` — it was
created `select r.*` before the column existed. Migration 20260813190000 fixed
the three SQL functions with the same problem and did not know about this
client-side read. Fixed here by reading the base table for the audience.
**The app has the identical bug at `src/services/trips/tripDocumentsService.ts:1431`
and it is not fixed** — out of scope, app side.

## 6. What this does not fix

**Staff still get no notifications about the trip.** The fan-out builds
`trip_admin_ids` from `group_trip_participants.role = 'host'` and does not know
the staff table exists, so a Manager misses every document and payment
notification. Known gap in the staff spec, out of scope here. The invite itself
does notify, because `invite_staff_member` sends it directly.
